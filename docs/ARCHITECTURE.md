# How PrettyTooltip works

This is a guide for working on the addon's code: how a tooltip becomes a panel, how the code is laid out, and why it was built this way. The user-facing features are in [README.md](../README.md), the tests in [tests/README.md](../tests/README.md), and the full taint and hidden-value audit in [tests/taint-safety.md](../tests/taint-safety.md).

## In one paragraph

PrettyTooltip never replaces or rewrites the game's tooltips. The game fills `GameTooltip` (or `ItemRefTooltip`, or a comparison tooltip) as usual. The addon then reads what the game filled, turns it into a plain Lua **model**, and draws its own frame, the **panel**, over it. The game's tooltip stays underneath. It is invisible (alpha 0) and padded to the panel's size, so the game's comparison anchoring and screen clamping still work. Whenever anything can't be read, fails, or the player holds the original-tooltip key, the panel hides and the game's tooltip comes back as it was.

```
 game fills GameTooltip ──► TooltipDataProcessor post-call (ns.Processor)
                                   │  stages, in a fixed order
         ┌─────────────┬───────────┴──────────┬──────────────┐
      "wording"     "panel"              "details"       "cursor"
   ItemLite.lua    Hooks.lua             Details.lua     Cursor.lua
   shorten item    read ─► model         detail rows     follow the
   lines on the    view ─► render        on the game's   mouse
   game's tooltip  refit + hide native   own tooltip
                                   │
                ┌──────────────────┴──────────────────┐
           panel (addon frame,               GameTooltip (alpha 0,
           TOOLTIP strata)  ◄── aligned to ──  padded to cover the panel)
```

## Code layout and load order

Files load in the order `PrettyTooltip.toc` lists them. Every file shares one namespace table, `ns`, from `local _, ns = ...`. Each layer only uses the layers loaded before it.

| Folder | What it holds | Notes |
|---|---|---|
| `Core/` | `Util.lua` (text helpers, safe access to hidden values), `Palette.lua` (colors by role and by school), `Settings.lua` (defaults, `ns.option`, styles, modifier keys) | No frames, no hooks. Settings are read when used, because saved variables arrive after the files run. |
| `Locale/` | `Locale.lua` (empty tables), `English.lua` (fallback for every client), then one file per language | Each language file has its own `[AllowLoadTextLocale …]` condition in the TOC, so a client loads only its own. |
| `Game/` | `Game.lua` (`ns.Game`, every question the addon asks the game, plus `ns.Processor`), `TooltipData.lua` (helpers every reader shares) | Readers get `ns.Game` passed in as an argument, so tests can pass a stand-in. |
| `Data/` | Static tables: schools, spell power coefficients, spell ranks, stat wording, disenchant results, herb/ore and skinning loot, node names | Most are generated by `tools/*.py` from Forever's client tables or CMaNGOS data. Don't edit those by hand. |
| `Panel/` | `Layout.lua` (panel frames, fonts, pixel snapping, chrome, the tooltip-type registry, `ns.ui`), `Render.lua` (`ui.renderView`, which draws a view) | Shared drawing only. A part that only one type draws lives in that type's file. |
| `Tooltips/` | One file per tooltip type: Item, Spell, Object, Unit, Aura, Quest, Macro, PetAction, Minimap, FlightPath | Each one registers itself with `ui.defineTooltipType`. |
| `Integration/` | How panels meet the game's tooltips: `Native.lua` (the hidden tooltip underneath), `Hooks.lua` (when to read and draw), `Details.lua`, `ItemLite.lua`, `Cursor.lua` | All hooking of Blizzard frames happens here (plus a few type-specific hooks in Quest and FlightPath). |
| `UI/` | Style editor, its samples and skin, options page, slash commands, debug report window, `/ptip capture` | `Capture.lua` sits between `#@debug@` markers, so release builds leave it out. |
| `PrettyTooltip.lua` | Startup | Loads last. On `ADDON_LOADED` it calls `ns.start()`, which migrates options, then installs each integration in order. |

Files return early when what they need is missing, for example `if not ns.Locale.supported or not TooltipDataProcessor then return end` in `Layout.lua`. On an unsupported client, the addon then installs nothing and the game's tooltips are left untouched.

## The life of a tooltip

### 1. The game hands over the data

`ns.Processor` (`Game/Game.lua`) is the addon's only connection to `TooltipDataProcessor`. It registers **one post-call per tooltip data type** and one `MODIFIER_STATE_CHANGED` watcher. The integrations add named **stages** to it, and these always run in the order `wording → panel → details → cursor`, whatever order they were added in. Each stage runs in its own `pcall`, so one failing stage is reported and the rest still run.

- **wording** (`ItemLite.lua`) shortens item stat lines on the game's own font strings, using `SetText` after the game has drawn them. The tooltip data stays untouched.
- **panel** (`Hooks.lua`) reads and draws the panel.
- **details** (`Details.lua`) adds the addon's detail rows (disenchant results, IDs, gathering loot, spell power) to the game's tooltip when no panel covers it.
- **cursor** (`Cursor.lua`) handles follow-cursor placement.

### 2. Deciding whether to draw (`Hooks.lua`)

`onTooltipData` gets a panel for the tooltip (one panel per game tooltip, created on first use by `ui.getPanel`). It asks the tooltip type for a **key** that names what is shown, such as an item link or a unit GUID, and then:

- If the type isn't restyled (`ns.restyles(option)` is false, or the layout is `"blizzard"`), or the original-tooltip key is held, it restores the native tooltip and stops.
- If this is new content (new key, new data type, or the panel is hidden), it draws at once.
- If it's a refresh of the same content, it keeps the old panel, refits, and checks again on the next frame. Other addons append their rows during that frame. A **fingerprint** of every shown line's text and color skips the redraw when nothing changed. The game re-sets shown tooltips often, comparisons most of all.

On first use it also hooks the tooltip (once):

- `Show`, `SetShown`, and `OnShow`, to refit and hide it again.
- `SetPoint`, to move comparisons next to the panels.
- `SetAlpha`, to keep it at 0 and remember the alpha the game wanted.
- `FadeOut`, `SetOwner`, and `OnHide`.

A 0.25 s `OnUpdate` poll catches lines added or rewritten in place after the fill, as the talent window does. `OnHide` and `OnTooltipCleared` don't tear the panel down right away. They wait a frame (`scheduleRestore`), because some owners clear and refill the same item, and an immediate teardown would flicker.

### 3. Read → model → view → render

Each tooltip type is a table registered with `ui.defineTooltipType(dataType, type)` in `Panel/Layout.lua`:

| Field | Meaning |
|---|---|
| `read(tooltip, data, game)` | Turns the game's data and lines into a **model**, a plain table such as `{ name, quality, stats, extras, … }`. It returns nil when anything can't be read. |
| `render(panel, tooltip, model)` | Draws the model. Most types build a **view** from the model and call `ui.renderView`. |
| `key(tooltip, data)` | Names what is shown, to tell new content from a refresh. |
| `option` | The setting that turns this type's panels on, such as `"itemPanels"`. |
| `details`, `detailKeys` | Optional. The detail rows the game's tooltip gets when this type isn't restyled. |
| `linesOnly` | For tooltips the game fills with lines and no data type (flight paths, Questie's quest links). Drawn through `ns.Hooks.renderLines`. |
| `alwaysRedraw` | Skips the fingerprint check, so the panel is redrawn on every refresh even when the lines read the same. Units use it. |

The split between reading and drawing is deliberate:

- **Readers** do all the parsing. They match the client's text against the game's own localized strings (`ITEM_MIN_LEVEL`, `DURABILITY_TEMPLATE`, …) through `util.unformat`, and ask `ns.Game` for anything the lines don't carry.
- **Views** are plain tables. `Render.lua`'s header comment documents their shape: header lines beside the icon, then sections of `prose`, `rows`, or `custom`, then a footer. `renderView` measures before it draws, so the panel's width is fitted to its content and measuring and drawing can't disagree.
- Because models are plain data, the **style editor's samples** (`UI/Samples.lua`) are just models written by hand and passed to the same `render`. The tests write out both the model and everything drawn.

### 4. Covering the native tooltip (`Native.lua`)

After a render, `refitNative` uses `SetPadding` to grow the hidden game tooltip until it's at least as big as the panel. Blizzard positions comparison tooltips, slides tooltips away from screen edges, and clamps them using the native frame's size. If the hidden frame were smaller than the panel, comparisons would land on top of it. Then:

- `alignPanel` pins the panel to whichever side (left or right) the tooltip itself is anchored by. Any leftover width difference then faces away from the frame the tooltip hangs from.
- `anchorToPanels` re-points comparison tooltips at the panels instead of the hidden tooltips beneath them.
- The fit has a fast path: `GetPadding` reports the applied padding, so the natural size can be worked out without a second layout pass. It skips sizes smaller than the largest seen for the same item, because right after `Show` the game can report a size before layout has finished. Those get checked again on the next frame.

`restoreNative` undoes all of this: original padding, original alpha, comparisons pointed back at the game's tooltip, and the panel hidden.

### 5. Fading world-unit tooltips

When the mouse leaves a world unit, the game fades its tooltip by setting alpha every frame from C. That bypasses the `SetAlpha` hook, so the hidden tooltip would show through. Hiding it with `Hide()` would run `GameTooltip_OnHide` under the addon's taint. So `fadeOut` **parks** the tooltip instead: it unclamps it, anchors it far off screen, and hides the panel. The game hides the tooltip itself when the fade ends. `unpark` (on `SetOwner`, `OnHide`, or new data) restores its anchors and clamping, but only while it's still parked, because the game or another addon may already have moved it.

## Taint and hidden values

WoW Forever hides many values in combat ("secret values"): unit data, aura fields, a tooltip's line text, and even its size. Blizzard code that touches an addon-written value runs tainted, and tainted Blizzard code then loses access to secret values, which shows up as Lua errors in Blizzard files blamed on the addon. Most of the design follows from this:

- **Read-only post-calls, no pre-call.** The processor reads tooltip data after pre-calls run, so anything an addon writes there taints the game's fill. Before 1.3, item wording replaced the data's line tables in a pre-call. Now it rewords the drawn font strings in a post-call.
- **Hooks never replace Blizzard functions.** The addon only uses `hooksecurefunc`, `HookScript`, and the processor's callbacks.
- **The addon never shows a hidden game tooltip and never hides a shown one.** `Show()` is only called on a tooltip that's already shown (to trigger a layout), because on a hidden one it runs `GameTooltip_OnShow`. Fading tooltips are parked rather than hidden (see above).
- **Every game value goes through a guard.**
  - `util.isSecret` checks `issecretvalue` and `canaccesstable`.
  - `util.call` rejects calls with restricted arguments or results.
  - `util.number`, `util.readable`, and `util.safeText` return nil for anything unusable.
  - `util.canModify` rejects forbidden or protected frames, and frames whose width can't be read.
  - Checks fail closed: when in doubt, the game's tooltip is restored.
- **Combat spell tooltips** keep their panel. A hidden line is kept as an opaque value and drawn by `ui.hiddenTextAt`, which hands it to a font string of the addon's own without reading, measuring, or comparing it. Font strings that once held a secret are never reused for readable text. Other readers (item, aura, unit) restore the native tooltip when a line is hidden.
- **Bookkeeping lives in addon-owned weak tables** (`setmetatable({}, { __mode = "k" })`), never as fields on Blizzard frames.
- **The health bar** is borrowed from the game and returned. Its value is never read, and `UnitHealth` is never called.
- **Follow cursor** anchors `GameTooltip` once to a 1×1 tracker frame that moves with the mouse. It never reparents the tooltip or moves it every frame.

[tests/taint-safety.md](../tests/taint-safety.md) lists every Blizzard API the addon calls, what can go wrong with each one, and how the guards and tests cover it.

## Localization

Readers match tooltips against the **game's own global strings**, which every client defines in its own language. That covers most of the parsing without translation. `Locale/` covers what the game has no string for:

- `ns.Locale.formats`, `descriptions`, `statWordings`, `schoolWords`, `skills`, `dispels`, `questTags`: wordings and names used to read the client's text.
- `ns.L["English text"]`: the addon's own words. Missing entries fall back to the English key through a metatable.
- `ns.Locale.supported` and `ns.Locale.features`: a language file turns the addon (and features such as spell coefficients) on only once captures of that language show them working. On an unsupported client the addon stays inactive rather than parsing wrongly.

`English.lua` always loads first as the fallback. The client's own language file then replaces what its language says differently.

## Settings and styles

`Core/Settings.lua` holds `DEFAULTS`. `PrettyTooltipDB` saves only the values the player changed (nil means default). `ns.option(key)` is read at the moment of use, never cached at load time. Every change bumps `ns.settingsVersion`, which is part of the fingerprint, so a panel drawn before the change gets drawn again.

`ns.ELEMENTS` lists every styleable part of every panel (fonts, sizes, colors). `ns.style(key)` and `ui.styleOf(key)` resolve a part's style from the defaults, the player's overrides, the global font scale, and LibSharedMedia fonts. The style editor (`UI/Editor.lua`) edits these and shows the change on a live sample panel.

There are two global layout modes:

- `"pretty"` draws panels for each type that's turned on.
- `"blizzard"` leaves every game tooltip in place and only adds the item wording and the detail rows.

## Static data

The game exposes no API for spell power coefficients, spell schools by rank, disenchant results, herb and ore contents, or skinning loot. The addon ships these as Lua tables in `Data/`. Generators in `tools/` build most of them from Forever's client tables (via wago.tools) or from CMaNGOS's Classic database. Rerun the generators when Forever changes, rather than editing the output. Tables are keyed by ID wherever possible, and names are looked up in the client's language at runtime (`game.localSpellName`, `Data/NodeNames.lua`), so the data works on every client.

## Other addons

These integrations are all optional, feature-detected, and called through `pcall`:

| Addon | Integration |
|---|---|
| DialogueUI | Backdrop art and quest parchment |
| EllesmereUI | Flat backdrop by default; respects its hidden health strip |
| Questie | Reads Questie's quest lines (drawn as a lines-only type) |
| Auctionator | Auction price row |
| LibSharedMedia | Extra fonts |
| Class-color addons (`CUSTOM_CLASS_COLORS`) | Unit class colors |

Rows that other addons append to a tooltip are collected by `TooltipData.appendedRows` and shown in the panel's "extras" section, in muted colors.

## Testing and release

The addon runs outside the game in Lua 5.1 (through Python's `lupa`):

- **Harness.** `tests/harness/wow.lua` stands in for the game, with frames, font strings, and textures that remember what was set on them, and fixed text metrics.
- **Fixtures.** Each one is a real tooltip captured in game with `/ptip capture`. It holds the data, the lines, and the answers to every `ns.Game` question the reader asked.
- **Expected outputs.** A test runs a fixture the way the game would (TOC order, `ADDON_LOADED`, the processor stages, read, render), then writes the model and every drawn string and texture with its position to `tests/outputs/`. Differences fail the test, and `--update` accepts them.
- **Variants.** `tests/variants.lua` reruns fixtures under other settings: the Blizzard layout, and optional parts turned off.
- **Unit checks.** `tests/unit/*.lua` cover hidden values, forbidden frames, combat, startup order, locales, and more.
- **Lint.** luacheck runs with `.luacheckrc`, which lists every game global the addon reads.

The CI workflow (`.github/workflows/ci.yml`) runs the tests and lint, builds with the BigWigs packager (`-d`, no publishing), and runs `tests/check_package.py` on the built zip. That script checks TOC load order, locale conditions, required files, that no development files are included (`tests/`, `tools/`, `docs/`, `*.py`, `UI/Capture.lua`), and that the addon starts in every locale. Pushing a `v*` tag runs the same checks and then publishes. `.pkgmeta` decides what's left out of the package, and `CHANGELOG.md` is the hand-written release notes.

## Key decisions, in short

| Decision | Why |
|---|---|
| Draw a panel *over* the game's tooltip instead of reskinning or rebuilding it | The game keeps owning tooltip lifetime, comparisons, and anchoring, and other addons keep adding lines to the real tooltip. The original is always one keypress (or one failure) away. |
| Keep the native tooltip invisible and padded to the panel's size | Blizzard's comparison layout and screen clamping use the native frame's bounds. |
| One processor post-call per type, with ordered stages | A fixed order (wording, then panel, then details, then cursor) whatever the TOC order. Each stage is isolated by `pcall`. |
| Post-calls only read; no pre-call | Writing into tooltip data taints the game's fill (1.3 removed the last pre-call). |
| Fail closed to the native tooltip | A wrong or broken panel is worse than the game's own tooltip. Every failure path calls `restoreNative`. |
| Separate reader, model, view, and renderer | Parsing can be tested field by field, samples are just models, and drawing is shared across types. |
| Inject `ns.Game` into readers | Tests replay captured game answers without a fake global API for everything. |
| Parse through the game's own localized strings | Most of every language works without translation. `Locale/` only holds what the game doesn't define. |
| Gate on `ns.Locale.supported` | An unverified language leaves tooltips untouched instead of parsing them wrong. |
| Read settings at use time; invalidate with `settingsVersion` | Saved variables arrive after files load, and changes apply to shown panels at once. |
| Park fading tooltips off screen instead of `Hide()` | `Hide()` runs `GameTooltip_OnHide` tainted. Moving a frame runs no Lua. |
| Defer teardown and redraw by one frame | Owners clear and refill the same content, and other addons append rows a frame later. Waiting avoids flicker and duplicate renders. |
| Generate static data offline | No game API exists for coefficients, schools, or loot tables. Generators keep them reproducible. |
| Capture-based regression tests | Tooltip text varies by client, language, and state. Real captures pin real behavior, and the expected outputs show exactly what a change alters. |

## Adding a tooltip type

1. Create `Tooltips/<Type>.lua` with `read`, a view builder, `render`, and `key`, and call `ui.defineTooltipType(Enum.TooltipDataType.<Type>, { … , option = "<type>Panels" })`. Return early at the top if the data type or `ui` is missing.
2. Add the file to `PrettyTooltip.toc` after `Panel/Render.lua` and before `UI/`.
3. Add `<type>Panels` (and an icon option, if any) to `DEFAULTS` in `Core/Settings.lua`. Give the type an entry in `ns.TOOLTIP_TYPES` (its `restyle` and `cursor` settings, and the data types it covers) and its styleable parts in `ns.ELEMENTS`.
4. Match the game's text through its global strings. Add anything the game doesn't define to `Locale/English.lua` and the language files. Add new game globals to `.luacheckrc`, then rerun `python tools/make_strings.py` so the tests know them in every language.
5. Add samples to `UI/Samples.lua` so the style editor can show the type.
6. Capture a few real tooltips with `/ptip capture`, import them with `tests/import_captures.py`, run `python tests/run.py`, and review the new expected outputs.
